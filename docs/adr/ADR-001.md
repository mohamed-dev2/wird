# ADR-001 — Local-first storage

Status: accepted (irreversible in practice)

## Context

Wird tracks highly personal religious practice daily. Early sketches
assumed a sync backend so users could move across devices; that also
implied storing identifiable behavioral data on a server, subject to that
server's operators, their jurisdiction, and breach risk.

## Decision

All data lives in `localStorage` on the user's device, behind a versioned
validation layer (`app/lib/schema.ts`). Offline is the _default_ state;
network is only ever used for user-initiated content fetches (see
`docs/NETWORK.md`). The app has no server, no accounts, no sync.

## Alternatives

- Firebase/Supabase sync + auth: rejected — storage of religious practice
  would be a server-side liability and a privacy contradiction for a
  worship tracker promised to be device-only.
- IndexedDB: seriously considered; faster for large corpora. Rejected for
  now because the datasets are small (< a few MB), `localStorage` is
  synchronous and simpler to keep migration-correct, and the SWR/migration
  guarantees of the schema layer apply equally. An IndexedDB adapter is the
  designated future escape hatch (see Consequences).

## Reason

Privacy is the product's core guarantee. Local-first removes the entire
class of server attacks and makes the privacy model auditable in one file
(DOCUMENTATION.md §4/§5).

## Consequences

- Users cannot sync across devices by login; moving data is via backup
  files or device-to-device QR/LAN transfer.
- `localStorage` quota (~5–10 MB) bounds dataset growth; audio/tafsir are
  fetched on demand, the mushaf is compressed.
- If we ever need larger local data, the correct migration is an
  IndexedDB **adapter behind the existing schema layer**, not a per-call
  rewrite — keep `lib/*` access going through `loadFromStorage` /
  `saveToStorage` / `useStoredState` so the swap is contained.
