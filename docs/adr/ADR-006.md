# ADR-006 — Localization strategy

Status: accepted

## Context

The product is passionate/religious and the original language is Arabic
(RTL). We needed a localization strategy that (a) keeps every user-facing
string in the dictionary, (b) survives a re-render without losing state,
(c) never localizes the religious text itself, and (d) is trivial for
contributors adding a language.

## Decision

A **flat, typed AR/EN dictionary** in `app/lib/strings.ts` (one object with
matching Arabic/English key sets — parity is CI-enforced) selected by a
reactive `Lang` type in `app/lib/i18n.ts` (`useT()` context hook). The
document root stays `lang="ar" dir="rtl"`; we render logical CSS properties
so a future LTR language needs no layout rewrite (`scripts/check-css.mjs`
enforces logical properties). Quran/hadith corpora stay in canonical
Arabic with curated translations as data, never as app copy.

## Alternatives

- ICU/rugged i18n library (react-intl, i18next): rejected — a flat
  dictionary with a `useT()` hook and zero runtime deps fits the
  no-new-dependencies policy and keeps the whole string surface greppable
  and diff-able in code review.
- Per-language JSON files outside the code: rejected — losing type
  checking and the parity gate; in-repo TS keeps the dictionary
  self-documenting and CI-checked.

## Reason

The dictionary is small (~800 keys); the main risks are missing keys,
renamed keys, and RTL layout breakage — all three are now enforced or
checked by automation.

## Consequences

- Adding a language = new object section + `Lang` union + dir handling
  (docs/HOW_TO_ADD_A_LANGUAGE.md). Pluralization is currently handled by
  key strategy (separate keys per count class) — documented limitation.
- New strings must be added to both AR and EN; the parity check in
  `docs:check` fails the build on imbalance.
- Insight/companion copy must pass the `guidance-safety` scan; prefixes
  like `cm:` mark guidance strings for automatic review.
