# ADR-005 — Quran data architecture

Status: accepted

## Context

The Quran viewer must work fully offline, searchable, in two display
languages plus tafsir on demand — while never sending the mushaf text
through a server we operate.

## Decision

The mushaf (Uthmani text), English translation (Clear Quran), and a tafsir
(Jalalayn, Arabic) ship as **compressed static JSON under `public/data/`**
(same-origin, so they are part of the deploy and the service worker).
Everything is kept in normalized small-object form (`ayah: {surah, ayah,
text, en, juz, key}`) produced by an offline build script — the JSON files
are generated artifacts (see `public/data/README.md`), never hand-edited.
Other tafsirs/hadith books load **on demand** from their canonical CDNs
(CSP-allowlisted) so the offline footprint stays tiny.

## Alternatives

- Ship all tafsirs + all hadith books: rejected — would multiply the
  bundle by an order of magnitude for a rarely-used subset. On-demand CDN
  fetches keep the app ~small and are explicitly opt-in.
- A remote mushaf API at runtime: rejected — the core text must not depend
  on network or on a third party we can't control.

## Reason

Offline mushaf reading is a top-tier feature for real users (data plans,
travel, and the `travel` privacy mode); a fixed, reviewable dataset also
allows correctness + attribution tooling (docs/HOW_TO_ADD_RELIGIOUS_CONTENT.md).

## Consequences

- `public/data/*.min.json` are **generated** — regenerate from source, do
  not edit by hand (enforced by a header note + review convention).
- Adding new hadith/tafsir sources means adding a CDN allowlist entry in
  next.config.ts CSP + a row in `lib/privacy.ts` NETWORK_ACCESS (both are
  code-level documentation of the network boundary).
- Quran text errors are rare but weigh heavily; the dataset pipeline must
  record source + verification hash (see the religious-content guide).
