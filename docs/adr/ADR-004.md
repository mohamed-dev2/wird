# ADR-004 — Privacy model

Status: accepted

## Context

The app stores daily counts, reviews, reflections, adaptive-guide state,
and transfer logs. We needed a single, documentable privacy contract that
contributors couldn't silently break.

## Decision

Four principles, codified in `docs/PRIVACY_ARCHITECTURE.md`, `lib/privacy.ts`
(data-sensitivity classification + network manifest), and the code gates:

1. **Everything stays local** — no server, no accounts, no sync.
2. **Only content the user asked for crosses the wire** — and only when
   they opt in (CDN tafsir/hadith/audio; see `lib/privacy.ts` NETWORK_ACCESS
   and docs/NETWORK.md).
3. **Exports are the only bulk-egress** — logged locally
   (`wird-export-log-v1`), integrity checked, requiring PIN re-entry for
   plain exports.
4. **Sensitive classes are treated specially** — `highly_sensitive` keys
   (reflections/vault) get at-rest encryption and are excluded from
   diagnostic exports; "hide names" and travel mode hide profile identity
   from casual viewers.

## Alternatives

- Rely solely on "be careful": rejected — a reviewable manifest is what
  makes an open-source privacy claim credible.
- Per-key encryption of everything: rejected — everything-encrypted
  becomes key-on-phone-next-to-encrypted-app, providing theater rather
  than safety, while breaking searches/analytics that legitimately read
  local counters.

## Reason

A verifiable, small privacy surface is the trust anchor of the product. If
a future contributor adds a network call, the manifest + CSP + docs:check++
gate makes it visible in review instead of hidden in a call site.

## Consequences

- New storage keys must be classified and must appear in DOCUMENTATION §4
  and (if sensitive) in `sensitivityOf()`.
- The privacy model can't be changed casually; ADR-004 is referenced by
  SECURITY.md and every feature doc claims compliance with it.
